## 补充

* **补充1**
```
Dify 有两重身份：
  · 对人：Web 控制台（也能经网关或内网访问）
  · 对系统：功能 API（工作流、Chat API 等）← 重点治理对象

它不是：
  · API 网关（不做全公司 WAF/统一身份总入口）
  · AI 网关（不做多模型 Token 总账与 Fallback 主责）
```


* **补充2

数据 API、报表、特征/标签服务通常对权限和脱敏要求更高。  
如果只是通过边缘网关做统一认证，可能无法满足：
- 行级权限。
- 列级脱敏。
- 数据血缘。
- 不同租户的数据隔离。

建议在数据应用**服务内部增加专门的数据权限层**。


* **补充3

 可观测性没有形成统一链路，**统一关联**：同一请求一条 trace_id 贯穿网关 → 应用 → 模型
 
* **补充4

安全方面
```
┌─ 边缘：API 网关 ─────────────────────────────┐
│  TLS · WAF · 认证 · 限流 · IP 策略 · 审计    │
└──────────────────┬──────────────────────────┘
                   │ 仅内网
┌─ 应用层：业务 / 数据 / Dify·RAGFlow ─────────┐
│  服务身份 · 租户隔离 · 输入校验 · 权限模型    │
└──────────────────┬──────────────────────────┘
┌─ AI 网关 ───────────────────────────────────┐
│  虚拟 Key · 模型白名单 · 预算 · 内容策略     │
└──────────────────┬──────────────────────────┘
┌─ 算力 / 数据面 ─────────────────────────────┐
│  网络隔离 · 密钥托管 · 镜像与供应链 · 脱敏   │
└─────────────────────────────────────────────┘
```


* **补充5

API网关职责

| 能力 | 说明 |
|---|---|
| **路由** | 按路径/域名把请求转到业务、数据、Dify、AI 网关等 |
| **身份认证** | API Key、JWT、OAuth，确认「谁在调」 |
| **授权** | 这个调用方能不能访问这条 API |
| **安全** | HTTPS、WAF、防刷 |
| **限流熔断** | 保护后端不被打挂 |
| **审计日志** | 谁、何时、调了什么 |
| **协议处理** | TLS 终止、有时做头转换等 |

* **补充6

- 指标：  Prometheus + Grafana（或云监控）
- 日志：  Loki / ELK；网关与审计日志单独索引
- 链路：  OpenTelemetry → Jaeger / Tempo
- AI 效果：Langfuse（模型与 Agent 语义）
- 告警：  错误率、P99、限流、预算、GPU 打满 → 值班通道
